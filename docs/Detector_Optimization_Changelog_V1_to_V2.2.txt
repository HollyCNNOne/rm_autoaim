  1. V1 — 原始版本（HSV 硬阈值）
================================================================================

【问题描述】
  - Step 4 使用硬 if 阈值过滤灯条候选，阈值过于严格

================================================================================
  2. V2 — 软评分 + CLAHE + 自适应形态学
================================================================================

【目标】
  解决 V1 的"零检测"问题，同时保持处理速度不退化。

【改动项】

  2.1 Step 1：CLAHE 增强颜色分离（extract_color）
  --------------------------------------------------------------------------
  问题：V1 的 HSV 阈值在高光/暗光场景下边缘不稳定，导致灯条断裂。
  方案：
    - 对 V 通道应用 CLAHE（clipLimit=2.0, tileSize=8×8），增强局部对比度
    - 动态 V 下界：v_low = mean(V) × 0.35，钳位 [60, 140]
      亮场景自动抬高阈值抑制反射，暗场景自动降低捕获弱灯条
    - 关键：mean(V) 必须在 CLAHE 之前计算，否则 CLAHE 改变分布后
      动态阈值对实际亮度"失明"
    - 红色三区间并集：H[0,8] ∪ H[5,30] ∪ H[170,179]（覆盖红/橙/琥珀色）

  2.2 Step 2：距离自适应形态学（apply_morphology）
  --------------------------------------------------------------------------
  问题：固定核大小无法适应远近目标的不同尺寸。
  方案：
    - 利用上一帧的平均灯条高度（prev_avg_lightbar_height_）自适应调整
      闭运算核大小：
        near  (h > 100px) → 9×9  （大目标需要大核填补间隙）
        mid   (h > 50px)  → 7×7
        far   (h < 20px)  → 3×3  （小目标大核会导致过度合并）
        default           → 5×5
    - 安全钳位：若 prev_avg_lightbar_height_ > 150px（疑似误检帧），
      强制降为 100px 避免当前帧小目标被过度合并
    - 开运算固定 3×3（噪声去除与尺寸无关）

  2.3 Step 4：放宽几何阈值（filter_light_bars）
  --------------------------------------------------------------------------
  问题：V1 的硬阈值砍掉了太多"可疑但可能真实"的候选。
  方案：阈值放宽约 20%，将边缘候选交给 Step 5 的代价函数做最终裁决。
    - kRelaxedMinAspectRatio: 0.05 → 0.04
    - kRelaxedMaxAspectRatio: 0.50 → 0.60
    - kRelaxedMinArea: 20 → 48
    - kRelaxedMaxArea: 8000 → 9600
    - kRelaxedMinConvexity: 0.40 → 0.50
  设计理念：Step 4 是"保安"（拦 80% 明显噪声），Step 5 是"HR 面试官"
  （对剩余边界案例做精细评分）。

  2.4 Step 5：软评分 + 滑动窗口 + 贪心冲突消解（pair_light_bars）
  --------------------------------------------------------------------------
  问题：V1 的硬 if 条件"全部满足才通过"导致边缘目标零配对。
  方案：用连续代价函数替代硬阈值，实现"哪个更好选哪个"。

  代价函数 compute_pair_cost（4 维加权）：
    权重：Height(0.45) + Angle(0.25) + Y-Offset(0.10) + X-Ratio(0.20)

    f1 高度相似度：h_cost = 1 - min(h_a, h_b) / max(h_a, h_b)
    f2 角度差：    ang_cost = min(|angle_diff| / 45°, 1.0)
    f3 Y 偏移：    y_cost = min(|y_a - y_b| / avg_h, 1.0)
    f4 X 间距比：  x_cost = min(|x_ratio - ideal| / 3.0, 1.0)
                   双尺度理想比：小装甲(avg_h≤60) → 2.45，大装甲 → 3.0

  算法流程：
    A. 按 center.x 排序（启用滑动窗口剪枝）
    B. 滑动窗口：对每个 i，检查 j∈[i+1, i+8)，x 距离超限则 break
    C. 所有候选对按代价升序排序（最优优先）
    D. 贪心分配 + used[] 冲突消解（每个灯条只能用一次）
    E. 代价阈值 kMaxPairCost=0.35，超过的直接丢弃
    F. 早期终止：已配对 ≥ n/2 时退出

  为什么用贪心而非匈牙利算法？
    经过 Step 4 后，每帧真实灯条通常 ≤ 6 个。在这种极小数据集上，
    贪心与全局最优不可区分，但时间复杂度 O(n·k·log(n·k)) vs 匈牙利 O(n³)。

  2.5 Step 1：ROI 前置
  --------------------------------------------------------------------------
  问题：V1 先处理全图再做 ROI，浪费 50% 的 CLAHE/inRange 计算。
  方案：detect() 入口处先取上半部分 ROI（bgr.rows/2），再送入 extract_color。

【实验结果】
  - 首次成功检测到装甲板（PnP depth=4.04m）
  - 但引入新问题：延迟增加 68%，帧丢失 34%
  - 出现多配对误检（2-3 个装甲板 vs 实际 1 个）

【涉及文件】
  - src/Detector.cpp（重写 extract_color, apply_morphology, filter_light_bars,
    pair_light_bars, compute_pair_cost）
  - include/rm_autoaim/Detector.hpp（新增 LightBar, ArmorPair 结构体，
    新增 prev_avg_lightbar_height_ 成员）


================================================================================
  3. V2.1 — 性能修复 + 阈值调优
================================================================================

【目标】
  解决 V2 引入的性能退化（68% 延迟增加）和多配对误检。

【改动项】

  3.1 性能修复
  --------------------------------------------------------------------------
    - 紧化 Step 4 阈值：convexity 0.32→0.38, area 16→18
      减少无效候选进入代价计算
    - 配对早期终止：pairs.size() >= n/2 时立即退出循环
    - 形态学冷启动保护：prev_avg_lightbar_height_ 初始化为 80.0F
      （保守默认 5×5 核），避免第一帧无历史数据时行为异常
    - 双尺度理想 X 比：小装甲(avg_h≤60) 用 2.45，大装甲用 3.0
      解决了 outpost 近端大装甲被错误惩罚的问题

  3.2 代价阈值过滤
  --------------------------------------------------------------------------
  问题：放宽阈值后，低质量配对（噪声+真实灯条）也通过了。
  方案：在贪心分配循环中增加 kMaxPairCost=0.35。
    for (const auto& sp : scored) {
        if (sp.cost > kMaxPairCost) break;  // 代价过高，丢弃
        ...
    }

【实验结果】
  - Detector 平均延迟：5799μs（-10.3% vs V1）
  - Detector 最大延迟：15653μs（-14.8% vs V1）
  - 成功检测目标，PnP depth=4.04m

【涉及文件】
  - src/Detector.cpp（阈值调整、早期终止、代价过滤）
  - include/rm_autoaim/Detector.hpp（ArmorPair 新增 cost 成员）


================================================================================
  4. V2.1+ — 反跨甲板 + 时序验证
================================================================================

【目标】
  解决黄色条带误识别和跨甲板配对问题。

【问题分析】
  核心发现：当正常装甲板灯条未能被检测到时（如转动过渡帧），算法
  没有参照物，会将黄色条带与其他噪声灯条强行配对，产生跨甲板误检。
  这是一类"缺失前置条件"的连锁错误，而非简单的阈值问题。

【改动项】

  4.1 垂直重叠度硬约束（compute_pair_cost）
  --------------------------------------------------------------------------
  问题：来自不同装甲板的灯条（如左装甲板的左灯条 + 右装甲板的右灯条）
  垂直投影不重叠，但仍被配对。
  方案：在代价函数开头增加硬拒绝逻辑。
    - 计算两个灯条的垂直投影区间 [top, bottom]
    - 重叠部分 < 较短灯条高度的 50% → 直接返回 cost=1.0（拒绝）
    - 重叠 ≤ 0 → 直接返回 cost=1.0（完全不重叠）
  理由：同一装甲板的左右灯条必然在同一水平线上，垂直投影高度重叠。

  4.2 高度比硬拒绝（compute_pair_cost）
  --------------------------------------------------------------------------
  问题：跨甲板配对的灯条高度差异巨大。
  方案：h_min / h_max < 0.65 → 直接返回 cost=1.0（拒绝）。

  4.3 时序长边验证（Step 6，detect 函数）
  --------------------------------------------------------------------------
  问题：当正常装甲板未被检测时，黄色条带+噪声配对没有参照物，
  无法通过几何约束过滤。
  方案：引入 EMA 平滑的装甲板长边长度追踪。
    - 新增成员变量 prev_avg_armor_long_edge_（初始值 0.0F）
    - 提取角点后计算 top_edge 和 bottom_edge 的长边
    - 若 prev_avg_armor_long_edge_ 已初始化（> 1e-4F）：
        ratio = long_edge / prev_avg_armor_long_edge_
        若 ratio > 1.5F → 拒绝（突变检测）
    - 否则用 EMA 更新：new = α × current + (1-α) × old, α=0.15
  理由：真实装甲板长边在连续帧间不会突变。若当前配对的长边
  远超历史平均（1.5x），则是跨甲板/噪声配对，应当拒绝。

  4.4 宽高比硬拒绝（Step 6）
  --------------------------------------------------------------------------
  问题：错误配对的矩形宽高比异常。
  方案：提取角点后计算 aspect = w/h，若 < 1.2 或 > 4.5 则拒绝。

  4.5 最终阈值定稿
  --------------------------------------------------------------------------
    - kRelaxedMinArea: 48.0（过滤黄色条带，保留真实灯条 area≥50）
    - kRelaxedMinConvexity: 0.50
    - 代价权重：Height(0.45) + Angle(0.25) + Y-Offset(0.10) + X-Ratio(0.20)
    - kMaxPairCost: 0.35

【实验结果】
  - 黄色条带误识别：已解决
  - 跨甲板配对：已解决
  - 多配对误检：已解决
  - 检测稳定性：显著提升

【涉及文件】
  - src/Detector.cpp（compute_pair_cost 增加垂直重叠、高度比硬拒绝；
    detect 函数 Step 6 增加宽高比、时序长边验证）
  - include/rm_autoaim/Detector.hpp（新增 prev_avg_armor_long_edge_ 成员）

================================================================================
  7. Pipeline 通信优化（帧丢失修复）
================================================================================

【问题】
  V2 阶段 Pipeline 线程间通信使用 mutex + condition_variable 的阻塞队列，
  导致严重的帧丢失和性能不稳定。

【尝试过的方案】

  7.1 有界阻塞队列（Bounded Blocking Queue, capacity=8）
  --------------------------------------------------------------------------
  方案：将 atomic<shared_ptr> 替换为 mutex+condition_variable 的阻塞队列。
  结果：引发 GCC 14 编译错误（<csignal> 中 sig_atomic_t 未声明、
  <chrono> 中 time_point 未定义），无法在目标环境编译。

  7.2 无锁 SPSC Ring Buffer
  --------------------------------------------------------------------------
  方案：实现无锁单生产者单消费者环形缓冲区。
  结果：下游帧丢失 94.7%（Detector→Tracker 几乎全部丢失），
  因为自旋等待消耗 CPU 导致调度器惩罚。

【最终方案】

  7.3 原子槽 + 版本号去重 + CPU_PAUSE
  --------------------------------------------------------------------------
  回退到原始 V1 架构：
    - Reader→Detector 使用 atomic<shared_ptr<FrameData>> 原子槽
    - 版本号 dedup：frame_version_ 原子递增，下游对比版本号去重
    - Reader 线程使用 CPU_PAUSE 指令代替 sleep_for(100μs)
      原因：sleep_for(100μs) 在 Linux 下实际延迟高达 1-10ms，
      导致错过帧。CPU_PAUSE 是纯用户态指令，无调度开销。
  结果：0.25% 帧丢失，稳定可靠。

【涉及文件】
  - include/rm_autoaim/Pipeline.hpp（原子槽 + 版本号）
  - src/Pipeline.cpp（reader_thread_fn 使用 CPU_PAUSE）


================================================================================
  8. 编译兼容性修复（GCC 14）
================================================================================

【问题】
  GCC 14 标准库中 <csignal> 和 <chrono> 存在 bug，当 <mutex>
  或 <thread> 被引入时触发编译错误。

【方案】
  - 回退 Pipeline 架构，移除 mutex 和 condition_variable
  - 恢复原子槽机制，避免触发 GCC 14 标准库 bug
  - 调整 main.cpp 头文件包含顺序（<csignal> 前置）

【涉及文件】
  - src/main.cpp（头文件顺序调整）
  - include/rm_autoaim/Pipeline.hpp（移除 mutex/condition_variable）
  - src/Pipeline.cpp（移除 frame_queue，恢复原子槽）


================================================================================
  总结
================================================================================

  V1 → V2.2 的核心演进路径：

    V1 零检测
      → V2 引入软评分+CLAHE+自适应形态学，首次检测成功但性能退化
      → V2.1 性能修复+阈值调优，恢复并超越 V1 性能
      → V2.1+ 增加垂直重叠/高度比/时序长边验证，解决跨甲板误检
      → V2.2 清理调试代码，最终交付版本

  关键设计决策：
    1. 连续代价函数替代硬阈值是"零→有"检测能力突破的根本原因
    2. 垂直重叠度 ≥ 50% 是最有效的跨甲板防御手段
    3. EMA 时序长边验证填补了"无参照物时无法拒绝异常配对"的盲区
    4. 原子槽 + 版本号去重是 Pipeline 线程通信的最优解（零锁、零拷贝、
      零调度开销）

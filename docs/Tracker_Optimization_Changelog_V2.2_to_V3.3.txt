================================================================================
  1. V2.2 — 原始版本（动态向量 + 匈牙利匹配）
================================================================================

【架构概述】
  - 动态 vector<TrackedArmor> 管理跟踪目标
  - 匈牙利算法做检测框→轨迹关联
  - 基于 IoU + 中心距离的代价矩阵
  - 无固定槽位，ID 按创建顺序递增

【问题描述】
  1. ID 爆炸：每个新目标分配新 ID（0, 1, 2, 3, 4...），ID 持续增长无上限
  2. 无 ID 复用：目标消失后原 ID 废弃，新目标继续分配更大 ID
  3. 遮挡后 ID 跳变：短暂遮挡导致目标重新识别，ID 从 0/1/2 变成 3/4/5
  4. 无租约机制：目标短暂漏检即被删除，重新出现时视为新目标

【实验结果】
  - 基础功能正常，ID 匹配在无遮挡时稳定
  - 运行一段后 ID 可达 50+，无法对应物理装甲板（只有 3 个）
  - 人走过遮挡 → ID 完全重排，下游 Predictor 状态机断裂

【涉及文件】
  - src/Tracker.cpp（V2 版本）
  - include/rm_autoaim/Tracker.hpp（V2 版本）


================================================================================
  2. V3.0 — 固定沙盘架构（ID 爆炸根治）
================================================================================

【目标】
  根治 ID 无限增长，将 ID 锁定在 0/1/2 三个槽位内循环使用。

【改动项】

  2.1 固定沙盘（fixed-slot architecture）
  --------------------------------------------------------------------------
  问题：动态 vector 导致 ID 只增不减。
  方案：
    - 用 std::array<TrackedArmor, 3> 替代 vector，3 个槽位对应 3 个物理装甲板
    - 每个槽位有固定 ID（0, 1, 2），ID 永不增长
    - 新增 slot_active_[3] 标记槽位占用状态
    - 新增 std::queue<int> free_slots_ 管理可回收 ID 队列

  2.2 租约机制（lease mechanism）
  --------------------------------------------------------------------------
  问题：目标短暂漏检即被删除，重新出现时视为新目标。
  方案：
    - 新增 slot_timeout_[3] 倒计时计数器
    - 每帧 Phase 1 对所有活跃槽位 timeout--
    - 只有 timeout 归零后才回收槽位到 free_slots_
    - kTimeoutFrames = 15（约 90ms @ 166.7FPS），容忍短暂漏检

  2.3 六阶段流水线（6-Phase Pipeline）
  --------------------------------------------------------------------------
  将 update() 拆分为 6 个清晰阶段：
    Phase 1: 倒计时（租约递减，超时回收）
    Phase 2: 构建活跃槽位列表（匈牙利输入）
    Phase 3: 匈牙利匹配（检测框→槽位关联）
    Phase 4: 执行匹配（更新 PnP，续租，物理校验）
    Phase 5: 新人分配（unmatched 检测框 → 空闲槽位）
    Phase 6: 未匹配槽位处理（由 Phase 1 倒计时兜底）

  2.4 代码重写
  --------------------------------------------------------------------------
  - Tracker.hpp 完全重写：从 vector 变为固定数组 + 循环队列
  - Tracker.cpp 完全重写：引入 6 Phase 架构
  - 新增 reset() 方法：槽位初始化、队列重置

【实验结果】
  - ID 永久锁定在 0/1/2 三个值内，不再增长
  - 遮挡后 ID 可恢复（取决于租约时长）
  - 基础跟踪功能正常

【涉及文件】
  - src/Tracker.cpp（完全重写）
  - include/rm_autoaim/Tracker.hpp（完全重写）


================================================================================
  3. V3.1 — 三项约束加固（匹配收紧）
================================================================================

【目标】
  在 V3.0 固定沙盘基础上，收紧匹配参数，减少误匹配和 ID 抖动。

【问题描述】
  - V3.0 的 IoU 阈值（0.15）过低，允许质量很差的匹配通过
  - 无中心距离约束，远处不相关的检测框也可能被匹配
  - 无可见目标数量上限，极端情况下可能同时输出 3 个 ID
  - 无几何验证，异常宽高比的噪声框可能被分配给槽位

【改动项】

  3.1 IoU 阈值收紧（Types.hpp）
  --------------------------------------------------------------------------
  问题：kIoUMin = 0.15 过于宽松。
  方案：kIoUMin 0.15 → 0.45。
  理由：前哨站装甲板在 166.7FPS 下帧间位移极小（< 10px），
  0.45 的 IoU 阈值在保证不丢帧的前提下有效过滤误匹配。

  3.2 中心距离硬约束（associate 代价矩阵）
  --------------------------------------------------------------------------
  问题：匈牙利算法只看 IoU，不看绝对位置。
  方案：在代价矩阵计算中增加 300px 中心距离硬约束。
    - center_dist > 300px → cost = 1.0（直接拒绝）
  理由：相邻帧同一目标中心位移不会超过 300px。

  3.3 最多 2 个可见目标（Phase 5）
  --------------------------------------------------------------------------
  问题：前哨站同一时刻最多 2 个装甲板可见（正面 + 侧面）。3 个同时出现
  意味着有误检。
  方案：kMaxVisibleTargets = 2，Phase 5 分配时检查 active_count >= 2 则跳过。
  理由：物理约束，防止误检占用槽位。

  3.4 几何验证（Phase 5 宽高比检查）
  --------------------------------------------------------------------------
  问题：异常宽高比的噪声框可能被分配。
  方案：Phase 5 分配前检查装甲板宽高比 aspect = w/h 在 [1.2, 4.5] 内。
  理由：前哨站装甲板物理尺寸决定其宽高比不会超出此范围。

【实验结果】
  - 误匹配率显著下降
  - ID 抖动减少
  - 无遮挡时 012 序列稳定

【涉及文件】
  - include/rm_autoaim/Types.hpp（kIoUMin 0.15 → 0.45）
  - src/Tracker.cpp（associate 增加中心距离约束，Phase 5 增加
    可见目标数限制 + 宽高比验证）


================================================================================
  4. V3.2 — 相位锁定（遮挡 ID 重排修复）
================================================================================

【目标】
  解决人走过遮挡塔台后 ID 顺序从 012 变为 021 的问题。

【问题分析】
  核心现象：遮挡前 012 完美循环，人走过挡住镜头（> 超时时间），
  三个槽位全部回收，free_slots_ = [0, 1, 2]。遮挡结束后装甲板重新出现，
  按队列顺序分配：第一个出现拿 0，第二个拿 1，第三个拿 2。
  但物理出现顺序可能是 2→0→1（塔台转过来的顺序），
  导致 ID 与物理装甲板的对应关系永久错位。

  根因：队列 free_slots_ 只记录"谁先超时"，不记录"物理装甲板是谁"。

【改动项】

  4.1 匈牙利代价矩阵相位奖励（associate 第一层软约束）
  --------------------------------------------------------------------------
  问题：匈牙利算法只看 IoU，不关心 ID 是否匹配预期相位。
  方案：在代价矩阵中注入相位奖励。
    - 周期锁定后，计算当前帧相位 → 预期 ID
    - 匹配到预期 ID → cost -= 0.10（轻微折扣）
    - 匹配到非预期 ID → cost += 0.02（轻微惩罚）
  关键：幅度（±0.10）远小于 IoU 代价（0~1），仅在平局时生效。

  4.2 Phase 5 倾向性复用（第二层软分配）
  --------------------------------------------------------------------------
  问题：Phase 5 从队列取号，不关心物理相位。
  方案：当预期 ID 对应的槽位空闲时，优先复用该槽位，而非从队列取号。
    - 仅当预期槽位 !slot_active_（空闲）时才触发
    - 若被占用，安全回退到队列发号

  4.3 周期自校准模块
  --------------------------------------------------------------------------
  新增 frame_counter_ 全局帧计数器 + 周期测量机制。
    - 冷启动：累计 7 个有效观测值 → 取中位数锁定周期
    - 锁定后：EMA 追踪（α=0.2），仅接受 ±20% 以内的新样本
    - 兜底：连续 10 次拒绝则重置校准

  4.4 匹配惯性（第三层硬兜底）
  --------------------------------------------------------------------------
  问题：A/B 长相接近时，IoU 微小波动（0.02）导致匈牙利"变心"。
  方案：记录上一帧检测框→槽位映射，当前帧相同配对直接 cost -= 0.30。
    - 惯性奖励 0.30 远大于 IoU 波动（0.02），锁死原配对
    - 仅当跨帧 IoU > 0.3 时生效（避免不相关检测框误匹配）

  4.5 周期漂移防护（三重防线）
  --------------------------------------------------------------------------
  问题：EMA 观测值存在系统偏差（遮挡导致帧差偏大），周期缓慢漂移。
  方案：
    - P0 硬边界：[200, 300] 帧范围，超出拒绝
    - P1 干净采样源：改用 ID 首次出现帧差，而非槽位回收帧差
    - P2 大跳检测：帧间隙 > 100 帧 → 仅重置相位原点，不更新周期

【实验结果】
  - 无遮挡时 012 序列继续稳定
  - 短暂遮挡（< 租约）ID 不跳变
  - 长时间遮挡（> 租约）ID 仍可能重排，但概率大幅降低
  - 周期值锁定在物理合理范围内

【涉及文件】
  - include/rm_autoaim/Tracker.hpp（新增 frame_counter_、周期测量、
    惯性匹配、相位奖励相关成员）
  - src/Tracker.cpp（associate 增加相位奖励 + 惯性奖励，
    Phase 5 增加倾向性复用，新增周期自校准模块）


================================================================================
  5. V3.3 — 物理引导跟踪（四大核心问题根治）
================================================================================

【目标】
  在 V3.2 基础上，不再强求"ID 永不跳变"，而是通过物理现实约束
  确保输出给下游的每一帧位姿都是平滑、连续、物理可解释的。
  即使"认错了人"，也绝不"指错路"。

【问题一：ID 分配的不确定性（顺序混乱 vs 死锁）】
  --------------------------------------------------------------------------
  现象：V3.2 的全局帧计数器（frame_counter）作为相位基准，属于"开环时间预测"。
  当 Detector 漏检或卡顿时，帧计数器依然在跑，导致相位与物理世界脱节。
  系统要么"过于敏感"（012 因微小扰动乱跳），要么"过于不敏感"
  （惯性奖励霸占坑位，导致 1、2 无法上线）。

  解决方案：期望 ID 状态机（视觉证据驱动）
    - 引入 expected_id 变量，代表"系统希望下一个出现的是谁"
    - 视觉证据驱动：只有当旧 ID 连续 5 帧没有被匹配到时，才推进到下一个 ID
    - 跳过容忍：如果下一个 ID 连续 8 帧未被检测到，判定物理缺失，允许跳过
    - 最大驻留时间：即使 ID 持续被匹配，超过 65 帧后强制推进（防止霸占）
    - 快速扫描模式：跳过发生后进入 3 帧快速扫描，推进阈值降为 2
    - 连跳刹车：连续 2 次跳过 → 强制刹车，等待真实检测框出现
    - 核心哲学：系统"倾向"于 0→1→2，但允许在物理证据确凿时打破顺序

【问题二：单帧 PnP 数值突变（极端野值）】
  --------------------------------------------------------------------------
  现象：depth 从 3m 突跳到 0.5m 或 15m；yaw 从 +95° 瞬变到 -127°；
  t_fly 从 150ms 飙升至 1849ms。

  根因：ID 错配或角点像素噪声（1 像素误差在 10m 外可换算为 20cm 误差），
  导致 PnP 解算出一个数学收敛但物理荒谬的结果。

  解决方案：物理一致性校验 + 硬边界截断
    - 变化率限幅：Δyaw > 30°/帧 → 拒绝，Δdepth > 2m/帧 → 拒绝，
      Δpitch > 15°/帧 → 拒绝。拒绝后使用上一帧有效值
    - 硬边界截断：depth ∈ [0.5m, 15m]，pitch ∈ [-30°, +30°]
    - 恢复保护：校验失败后 1 帧内 EMA α 降为 0.30，防止"瞬间跳回"
    - 心跳解锁：连续 20 帧数值完全不变 → 强制重置平滑状态
    - 强制切换首帧保护：dwell timeout 或 skip 触发切换后，
      首帧复用历史位姿而非原始 PnP
    - 核心哲学：无论 PnP 在数学上是否收敛，只要结果违背物理常识，
      系统必须毫不犹豫地拒绝它

【问题三：渐进式漂移导致 EMA 基线失准】
  --------------------------------------------------------------------------
  现象：t_fly 从 150ms 缓慢爬升至 800ms 后，即使目标实际回到近端，
  EMA 输出的值依然偏高，导致"趋势滞后"。

  根因：传统 EMA 是"有记忆"的。渐进式毛刺（150→400→600→800）
  虽然每帧变化率不大，没有触发单次截断，但它会缓慢地、不可逆地
  将 EMA 基线拉高。

  解决方案：中位数锚定 + 偏差限幅
    - 维护长度为 15 的"可信历史窗口"，存储所有通过倍率截断的有效值
    - 计算窗口的中位数作为当前"基线"（不受单次或渐进毛刺影响）
    - 将当前测量值减去基线得到"偏差"，将偏差限幅在基线值的 ±30% 以内
    - 将限幅后的偏差加回基线，得到"干净测量值"，再送入 EMA（α=0.25）
    - 核心哲学：拒绝用"错误值"去移动"稳定基线"

【问题四：角度跨边界反转（Yaw 的 ±180° 陷阱）】
  --------------------------------------------------------------------------
  现象：yaw 在 +179° 和 -179° 之间震荡，或在 ID 错配时直接从 +95°
  跳变到 -127°，导致云台剧烈抽搐。

  根因：欧拉角（atan2）在角度接近 ±180° 时存在奇异性。传统的标量 EMA
  无法处理"圆形边界"（它会把 +179° 和 -179° 平均成 0°，造成完全错误的
  物理方向）。

  解决方案：四元数 SLERP（球面线性插值）
    - 内部计算：完全放弃欧拉角的标量 EMA，改用四元数 SLERP 进行姿态平滑
    - 四元数在四维空间中是连续的，没有奇异性
    - 插值路径永远走"球面上最短弧"，天然处理 ±180° 边界
    - 核心哲学：改变姿态的数学表示法（从欧拉角切换到四元数），
      从根源上根治角度不连续的问题

【实验结果】
  - ID 顺序正确率从 70% 提升至 95% 以上
  - PnP 极端毛刺（如 t_fly=1849ms）被彻底拦截
  - 角度输出零跳变，云台动作丝滑
  - Detector 平均延迟 5.5ms，丢帧率 < 1%
  - 系统能够无限期维持在稳定的 012 循环中

【涉及文件】
  - include/rm_autoaim/Tracker.hpp（新增 expected_id 状态机、物理校验、
    中位数锚定、SLERP、匹配惯性、刹车等相关成员，约 30 个新增字段）
  - src/Tracker.cpp（重写 associate 代价矩阵、Phase 5 分配逻辑、
    新增后处理平滑管线，约 200 行新增逻辑）
  - include/rm_autoaim/Types.hpp（ArmorPose 新增 pitch/yaw 字段）

================================================================================
  7. 总结
================================================================================

  V2.2 → V3.3 的核心演进路径：

    V2.2 动态向量 + ID 爆炸
      → V3.0 固定沙盘 + 租约机制，ID 锁定在 0/1/2
      → V3.1 收紧匹配参数（IoU 0.45、中心距离 300px、最多 2 目标）
      → V3.2 相位锁定 + 周期校准 + 匹配惯性，减少遮挡后 ID 重排
      → V3.3 物理引导跟踪：期望 ID 状态机 + 物理一致性校验 +
        中位数锚定 + 四元数 SLERP，彻底根治四大核心问题

  V3.3 的终极哲学：
    我们不再强求"ID 永不跳变"，而是接受物理世界的噪声与遮挡，
    通过"物理现实约束（Physics-Guided Constraints）"确保输出给
    下游的每一帧位姿都是平滑、连续、物理可解释的。
    即使"认错了人"，也绝不"指错路"。

  关键设计决策：
    1. 固定沙盘（3 槽位）是 ID 爆炸的根本解，而非参数调优
    2. 视觉证据驱动的状态机优于开环时间预测（帧计数器）
    3. 物理一致性校验是 PnP 毛刺的最后防线，比任何滤波器都可靠
    4. 中位数锚定解决了 EMA 无法处理的渐进式漂移问题
    5. 四元数 SLERP 是 ±180° 角度边界的唯一正确解法
    6. 匹配惯性（-0.30 奖励）以极低成本解决了匈牙利算法的瞬时记忆缺失
    7. 连跳刹车机制防止了无目标期的相位空转风暴
